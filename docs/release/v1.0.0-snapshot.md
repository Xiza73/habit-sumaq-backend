# v1.0.0 Snapshot + Restore Procedure

> **Playbook obligatorio** para el refactor `accounts-to-modular-finance` (v0.3.x → v1.0.0).
> Este doc se ejecuta DOS veces: una vez antes de **Phase A1** (BackfillCurrencyPools, que muta
> `accounts.balance`) y una vez antes de **Phase A7** (DropAccountsTable + DropTransactionsTable,
> punto de no retorno irreversible).

## Por qué este doc existe

El refactor a v1.0.0 toca las dos tablas más críticas de la app (`accounts`, `transactions`)
y termina con un DROP irreversible. Los rollbacks de Phase A1-A6 funcionan con
`pnpm migration:revert` + git revert. **Phase A7 NO tiene rollback transaccional** — la única
forma de volver atrás es restaurar desde snapshot.

Para que el snapshot sea recuperable, tenemos que:

1. Saber cómo crearlo (secciones 1 y 2)
2. Saber cómo restaurarlo (sección 3)
3. Saber cómo verificar el resultado (sección 4)
4. Tener un plan B si la UI de Railway falla (sección 5)

## 3. Restore procedure (rollback catastrófico)

**Cuándo invocar este flujo**:

- Phase A1-A6: si el `revert deploy + migration:revert + git` falla y la prod queda inconsistente
- Phase A7: cualquier escenario que requiera volver atrás, dado que A7 no tiene otro camino

**Decision tree**:

```
¿La prod está broken?
├── SÍ, y la phase actual es < A7:
│   ├── 1° intento: rollback del último deploy en Railway (botón "Rollback" del UI)
│   ├── 2° intento: pnpm migration:revert desde local con DATABASE_URL apuntando a prod
│   └── Si 1 y 2 fallan o dejan inconsistencia → RESTORE COMPLETO (steps abajo)
├── SÍ, y la phase actual es A7:
│   └── RESTORE COMPLETO inmediato — no hay otro camino
└── NO: no restaurar. Pensarlo dos veces.
```

**Steps del restore completo**:

1. **Pausar el backend** — en Railway, pause el servicio backend
   (`[TODO: nombre del servicio backend]`) para que no entren writes durante el restore
2. Ir al servicio Postgres → tab **Backups**
3. Encontrar el snapshot relevante (label `pre-a1-...` o `pre-a7-...`)
4. Click **Restore** — Railway abre un dialog de confirmación
5. **CONFIRMAR que entendés que estás SOBREESCRIBIENDO la DB actual**
6. Esperar que el restore complete (`Restored`, no `In progress`)
7. Re-iniciar el servicio del backend
8. Correr la verificación de la sección 4
9. Si todo OK → rollback exitoso. Si NO → ir a sección 5 (pg_restore manual).

**Tiempo estimado**: 10-30 min según el tamaño de la DB.

## 4. Verificación post-restore

Correr en orden. Si alguno falla → NO declarar el restore exitoso.

- [ ] **Conexión a Postgres** (vía Railway shell o `DATABASE_URL`):

  ```sql
  SELECT current_database(), current_timestamp;
  ```

- [ ] **Versión del schema** (última migration debe ser la previa al snapshot):

  ```sql
  SELECT name FROM migrations ORDER BY timestamp DESC LIMIT 5;
  ```

  La última fila debe ser la migration ejecutada ANTES de la que estábamos por correr cuando
  hicimos el snapshot.

- [ ] **Cuenta de usuarios** (sanity check):

  ```sql
  SELECT COUNT(*) FROM users;
  ```

  El número debe coincidir con producción pre-snapshot.

- [ ] **Login** con la cuenta de testing `[TODO: email de testing]` funciona end-to-end
- [ ] **Web reconnect**: el frontend (Vercel) responde sin errores 500 en `/accounts`,
  `/transactions`, `/budgets`, `/alerts` en las primeras llamadas post-restore

Si todo verde → restore declarado exitoso.

## 5. Plan B: `pg_dump` / `pg_restore` manual

Si la UI de Railway no responde (outage, sesión bloqueada, etc.) podés snapshotear y restaurar
desde tu shell directamente.

### Crear dump manual

```bash
# Obtener la connection string desde Railway → servicio Postgres → tab "Connect" → "Postgres Connection URL"
# Guardarla en una variable local — NO commitear nunca al repo
export RAILWAY_PG_URL="postgresql://user:pass@host.railway.app:port/db"

# Dump en formato custom (recomendado, más portable que SQL plano)
pg_dump "$RAILWAY_PG_URL" \
  --format=custom \
  --file=habit-sumaq-snapshot-$(date -u +%Y%m%dT%H%M%SZ).dump

# Verificar que el archivo es legible
pg_restore --list habit-sumaq-snapshot-*.dump | head -20
```

### Restaurar dump manual

```bash
# CUIDADO: esto SOBREESCRIBE la DB target. Asegurate del environment.
pg_restore --clean --if-exists --no-owner --no-privileges \
  --dbname="$RAILWAY_PG_URL" \
  habit-sumaq-snapshot-<fecha>.dump
```

### Cosas que pueden fallar

- **Permisos de superusuario** para `DROP SCHEMA` durante `--clean`: pedile SUPERUSER al admin
  del Railway DB
- **Versión de `pg_dump` local distinta a la del server**: usá la más nueva
  (`pg_dump --version` y `SELECT version();` en el server)
- **Network timeout durante el restore**: agregá `--jobs=4 --verbose` para paralelismo y progreso
